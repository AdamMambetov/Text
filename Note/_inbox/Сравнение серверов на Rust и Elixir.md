# Сравнение серверов на Rust и Elixir

> Я узнал про язык программирования Elixir, на нём можно написать надёжный сервер. Чем сервер на Elixir будет лучше, чем на Rust? По тестам, которые я провёл с другом, сервер на Rust намного быстрее, чем на Elixir. Как их вообще сравнивать, если не по количеству одновремменных запросов?

Ответ от MiMo-V2.6-Flash Free:

## Короткий ответ

Rust и Elixir решают разные задачи. Rust быстрее в **сырой производительности** (пропускная способность на ядро, задержка на запрос), а Elixir сильнее в **конкурентности, отказоустойчивости и предсказуемости под нагрузкой**. Сравнивать их «по количеству запросов» — значит сравнивать то, где Rust выигрывает by design.

## Почему Elixir не «медленный», а другой

BEAM (VM Erlang) спроектирован под миллионы одновременных лёгких процессов с изолированным памятью и стеком. Там, где Node/Go-процесс — это поток OS, на BEAM процесс весит ~2 КБ. Отсюда:

- **Let it crash + супервизоры** — процесс падает, супервизор его перезапускает, сервер не умирает. В Rust за такую же изоляцию вы платите руками (акторы, каналы, `catch_unwind`).
- **Hot code reload** — обновление логики без рестарта и разрыва соединений.
- **Распределённость из коробки** — несколько узлов выглядят как одно приложение, `:global`, `:pg`, передача процессов между нодами.
- **Предсказуемый p99/p999** — у Rust выше средняя скорость, но при всплеске нагрузки и оверклоуе тайлы могут взлетать. BEAM держит хвост латентности ровным.

Именно поэтому Elixir ставят в телеком (WhatsApp — 2 млн соединений на один узел), финтех-шлюзы, IoT, чаты, биржевые диспатчеры.

## Как сравнивать честно

Кроме RPS смотрите на:

1. **Хвостовую латентность** — p50 / p95 / p99 / p999, а не среднее. Это главная метрика для «ощущения» сервера.
2. **RPS на ядро** — относительная эффективность, а не абсолютная (иначе решает только число ядер).
3. **Потребление памяти на соединение** — важно при 100k+ одновременных клиентах.
4. **Поведение при перегрузке** — что происходит, когда нагрузка превысила capacidad: очередь и деградация или отказ/разрывы. Rust-сервер без таймаутов часто падает, BEAM-сервер — «тормозит, но живёт».
5. **Время восстановления после сбоя** и процент успешных запросов в аварийный период.
6. **Скорость разработки и стоимость владения** — время на фичу, сложность релиза, стоимость серверов в месяц.

## Провайдьте тест правильно

Частые ошибки в «домашних» бенчмарках:

- Сравнивают **axum/actix** (raw TCP, минимум аллокаций) с **Phoenix** (HTTP/1.1, JSON, мидлвары) — это разные задачи. Сравнивайте полные стеки: Phoenix/Bandit против axum/actix, оба с одинаковой логикой.
- Забывают про **warmup** (JIT/кэши) и прогрев BEAM.
- Не учитывают **coordinated omission** — используйте `oha`, `k6`, `wrk2`, а не голый `wrk`.
- Тестируют на одном ядре vs всех ядрах, или с разными значениями keep-alive.

## Практический выбор

| Задача | Выбор |
|---|---|
| CPU-bound: парсинг, шифрование, видео, логика на CPU | **Rust** |
| Максимум RPS на минимальном железе | **Rust** |
| 100k–1M одновременных соединений, чаты, пуши | **Elixir** |
| Soft real-time с ровным p99 | **Elixir** |
| Распределённый кластер с самоисцелением | **Elixir** |
| Микросервис, где нужна и скорость, и надёжность | Гибрид: Elixir-оркестрация + Rust-NIF (`Rustler`) на горячие пути |

**Итог:** если ваш тест мерил RPS на одиночном запросе — он проверил именно то, где Rust сильнее. Добавьте замер p99 под нагрузкой на 100k соединений и сравните поведение при перегрузке — картина станет существенно интереснее.
